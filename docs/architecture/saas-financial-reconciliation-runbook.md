# SaaS Financial Hub reconciliation — inactive Phase 4

This is an independent read-only audit. The runner does not approve payments, change subscriptions or delivery state, create financial events, or alter the group-finance pull export. It remains off by default. Migration 030 adds only reconciliation tables. Do not merge migrations 029 or 030 into automatically deploying main without deployment coordination, isolated SQL Server validation, and review with Tarek.

## Verified Hub contract

The runner signs each exact JSON body with the active source-scoped HMAC credential and the reconciliation path POST /api/saas-financial/v1/reconciliation/events. This differs from ingestion's canonical path. The same key currently permits ingestion and inventory; there is no separate read scope. Never use DRVO_GROUP_FINANCE_EXPORT_TOKEN. Each page has a new timestamp and nonce. HTTPS, no redirects, a five-second connection limit, a 15-second total limit, a 16 KiB response cap, and a 20-event page limit apply. The process waits five seconds between pages, consuming at most 12 of the Hub's 30 requests per minute per IP. Operators must coordinate other clients sharing the IP.

The default run is a full inventory with no acceptance window and a page limit of 20; the Hub also supports an empty-object request for the first full-inventory page. Optional DRVO_SAAS_FINANCIAL_RECONCILIATION_ACCEPTED_FROM and DRVO_SAAS_FINANCIAL_RECONCILIATION_ACCEPTED_BEFORE supply a paired half-open UTC [from,before) Hub acceptance window. They must be valid seconds with up to six fractional digits and Z. A cursor continuation repeats the exact normalized window. The runner follows opaque cursors through empty pages with has_more=true and rejects repeated cursors, changing scan identity, malformed fields, non-string money/IDs, and out-of-order Hub IDs. It never converts Hub IDs or decimal-string amounts through JavaScript numbers.

Each invocation reads at most 15 pages and admits new requests only within a 90-second deadline; an admitted request can take up to 15 seconds more. A persisted PAUSED run resumes on the next invocation from its saved cursor; 1,000 pages is the hard total cap. A run older than 24 hours is marked SCAN_INCOMPLETE and a fresh run starts. Only a traversal with has_more=false receives a comparison status. A network, 401/403, 429, 5xx, invalid cursor, response, local-evidence, or database failure leaves the scan incomplete. No automatic retry loop masks an error. The next controlled invocation starts fresh after an incomplete run. A hard process stop leaves SCANNING; after ten minutes without progress, a later invocation may resume it. Page observations and cursor progress are committed in one SQL transaction. A terminal page can be finalized after a crash without refetching it.

## Evidence and meaning

The local side reads TblManualPaymentRequest directly for approved InstaPay requests with persisted review time at or after the verified capture cutoff. ReviewedByUserID and ApprovedSubscriptionID are checked as approval evidence. The SQL decimal amount and DATETIME2(7) review timestamp are read as text. Pre-cutoff approvals are deliberately excluded. A separate source-scoped outbox query reads up to 5,000 rows; any larger local population causes an incomplete scan until the bound is reviewed and raised. The Hub side consists only of events observed in this run. This three-way comparison finds missing outbox rows, pending/dead delivery, Hub events without eligible approvals, identity, amount, currency, occurrence-time and payload conflicts, and duplicate local or observed identities. A pending delivery is labeled DELIVERY_PENDING; an acknowledged outbox event absent from a full observed inventory is HUB_NOT_OBSERVED_PROVISIONAL. Window scans cannot infer that a local operation is missing from the Hub because its acceptance time is unknown.

OBSERVED_MATCHES_PROVISIONAL means this completed traversal found no discrepancies within its scope. DISCREPANCIES_OBSERVED means at least one finding was recorded. SCAN_INCOMPLETE means no comparison conclusion. NOT_RECONCILED is the disabled state. None means certified completeness. Hub rows can commit late below a scanned ID, or be accepted later with old occurrence time. Neither has_more=false, the scan's upper Hub ID, nor its acceptance interval proves that all source operations are visible. The upper ID is diagnostic only; it is never a permanent watermark.

TblSaasFinancialReconciliationEvent stores accepted Hub facts by source and event ID with a unique Hub ID. TblSaasFinancialReconciliationObservation records membership in each run. TblSaasFinancialReconciliationRun stores scope, progress, provisional upper ID, and bounded error code. TblSaasFinancialReconciliationCase and TblSaasFinancialReconciliationFinding preserve discrepancy state and each run's history. No case is automatically marked resolved, including after a later matching observation. Investigation states OPEN, INVESTIGATING, and RESOLVED require an operator decision with external evidence. No HMAC secret, signature, complete request, customer detail, or full response is stored or logged.

## Operation and recovery

Before any future activation, confirm the Hub source's immutable first activation, the separately approved capture cutoff, credential validity, shared replay cache, synchronized clocks, migration 029/030 in an isolated SQL Server, IP rate-limit capacity, and alerts. Then enable capture, delivery, and reconciliation in controlled separate steps. The Phase 4 commit does not set any flag, start a service, or configure a schedule. With configuration verified, run npm run saas-financial:reconcile from a separately supervised process; a disabled invocation exits without opening SQL or sending HTTP. Repeated invocations should include fresh overlapping acceptance windows and periodic full audits from activation. An operator can run two overlapping UTC intervals by setting the paired window variables for each invocation, and remove them for a full audit. Complete or failed runs start new scans without a cursor; only paused/interrupted runs resume.

Monitor last completed run time, PAUSED/SCAN_INCOMPLETE age, page and event counts, error codes, pending delivery, and open cases by verified SourceKey. Review APPROVAL_MISSING_OUTBOX against the authoritative approval transaction and migration/capture boundary; never synthesize a historical Hub event automatically. Review DELIVERY_PENDING in the delivery backlog; it is distinct from a missing outbox record. For HUB_NOT_OBSERVED_PROVISIONAL, repeat a fresh full scan after a quiet period and inspect the Hub acceptance record and delivery acknowledgement. For Hub-only, amount, identity, currency, or timestamp findings, preserve the original accepted event and collect independent evidence before an operator changes case state. If an interrupted scan has an invalid cursor or changed source boundary, mark it incomplete and start a fresh scan. Correct credentials or rate-limit scheduling before retrying authentication or 429 failures. Never edit immutable outbox payloads or accepted Hub events.

The runner logs only run ID, status, counts, and bounded error codes. Protect the HMAC credential as a server secret and keep the dedicated secret environment variable out of process output and shared logs. Its credential has ingestion authority as well as inventory authority; restrict access accordingly. Do not publish scan output or case data to customer-facing surfaces.
